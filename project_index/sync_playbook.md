# sync_playbook.md

## 1. 目的
把内部版已验证的 memory 改动，安全、可追踪地同步到发布版。

## 2. 标准流程

### Step 1：同步任务立项
- 输入：内部版修复结论（问题、根因、补丁思路、验证结果）。
- 输出：同步任务卡（影响模块、风险等级、目标版本）。

### Step 2：差异识别
- 对比同源模块差异（通常在 `memory/` 下）。
- 标记变更类型：
  - 逻辑修复
  - 接口行为变更
  - 测试补充
  - 文档补充

### Step 3：发布版适配
- 只迁移“发布版职责范围内”的变更。
- 删除任何内部业务耦合依赖。
- 保持发布版接口兼容（除非明确版本升级策略）。

### Step 4：验证
- 最低要求：
  - 三接口烟测
  - 与本次变更强相关的回归测试
- 推荐：
  - 真实 LLM 烟测（若变更涉及 query/LLM/fallback）

### Step 5：文档同步
- 必须更新：
  - `project_index/work_history.md`
  - `project_index/TODO.md`
  - 若行为变更，更新 `docs/python_api_guide.md` / `docs/cli_guide.md` / `docs/jsonrpc_methods.md`

### Step 6：验收收口
- 验收人可按“问题->根因->补丁->测试->文档”链路复核。
- 未满足链路完整性的同步任务不得标记完成。

## 3. 最小检查清单
- [ ] 同步范围已明确（模块与接口）。
- [ ] 发布版代码已落地。
- [ ] 对应测试已通过。
- [ ] 索引与对外文档已更新。
- [ ] work_history 已记录版本号、日期、影响范围。

## 4. 回滚策略
- 一旦发布版发现回归：
  1. 立即回滚发布版补丁。
  2. 在 `troubles.md` 记录事故。
  3. 回到内部版继续验证后再二次同步。

## 5. 常见失败模式与预防
- 失败模式：只抄代码，不抄验证上下文。
  - 预防：同步单里必须有复现步骤和验收标准。
- 失败模式：文档晚于代码，下一线程接不上。
  - 预防：把文档更新作为同步流程固定步骤，不可跳过。
- 失败模式：把内部版临时逻辑直接放进发布版。
  - 预防：Step 3 强制做“发布版适配审查”。
