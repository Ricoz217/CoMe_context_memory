## 1. 项目介绍

### 1.1 项目的目的与用途
- 项目目的：构建一个可持续维护、可压缩治理、可递归检索的上下文记忆系统，用于增强 LLM 在长周期任务中的“记忆连续性”和“可追溯性”。
- 核心用途：
  - 作为 Agent 的长期记忆底座，支持 Python/CLI/JSON-RPC 三种接入。
  - 在无向量数据库前提下，基于桶树与事件流实现可解释检索与治理（query/optimize/compress/split）。
  - 为复杂研发场景提供“可回放、可排障、可版本化”的记忆演进机制。

### 1.2 项目当前阶段
- 当前阶段：已发布“最低可运行版本”（发布版 `v0.3.2`），核心链路可用（入库、查询、压缩、拆桶、优化、三接口调用）。
- 阶段判断：项目已具备基础可用性，但仍处于“持续工程化”阶段。
- 仍未完全落地的方向：
  - 智能能力增强（更稳健的 fallback、评分可解释性、复杂场景治理策略）。
  - 结构化升级能力（schema migration 体系）。
  - 新想法落地（如 RTK/HEADROOM 记忆分类、更强的压力治理与可观测字段）。

## 4. 交接工作流（新 Agent 必读）

### 4.1 当任务是“定位/改 bug”
1. 读 `map.md`，确认入口与模块链路。
2. 读 `invariants.md`，确认不可破坏规则。
3. 读 `troubles.md`，看是否命中历史事故。
4. 再读 `work_history.md`，找相关里程碑与既有修复。
5. 最后看 `TODO.md`，确认是否已有同主题在排队。

### 4.2 当任务是“同步内部版改动到发布版”
1. 先读 `repo_strategy.md`。
2. 按 `sync_playbook.md` 的步骤执行。
3. 完成后更新 `work_history.md` + `TODO.md`。

### 4.3 当任务是“新增能力/改接口”
1. 先读 `contracts.md`（兼容性约束）。
2. 再读 `code_detail.md`（历史 tradeoff 与风险）。
3. 若涉及结构迁移，额外检查 TODO 中 migration 主题。

## 5. 本索引内各文件职责
- `map.md`：代码地图、模块职责、入口与热区。
- `contracts.md`：公开接口与稳定语义契约。
- `code_detail.md`：设计原因、历史决策、风险点、排障经验。
- `invariants.md`：硬性不变式，违反即高风险。
- `assumptions.md`：协作偏好、默认策略、非目标边界。
- `work_history.md`：里程碑演进（含版本号/日期/影响范围）。
- `troubles.md`：复发问题与标准处置。
- `TODO.md`：统一排期清单（含目标版本与验收）。
- `repo_strategy.md`：双仓治理模型。
- `sync_playbook.md`：同步执行手册。

## 6. 维护要求
- 每次重大修复完成后，至少更新：`work_history.md`、`TODO.md`、`troubles.md`（若是新问题类型）。
- 若对外行为改变，必须同步更新 `contracts.md` 与对应用户文档。
- 任何时候不得让“模板文档比代码还旧太多”。
