# repo_strategy.md

## 1. 治理目标
- 在“双仓并行”模式下保证开发速度与发布稳定性同时成立。
- 防止“内部试验逻辑直接污染发布版”与“修复漏同步”两类事故。

## 2. 角色定义
- 内部版（试验田）：
  - 负责快速验证复杂逻辑、容错路径与高压场景。
  - 允许临时实现，但必须保留可解释的结论。
- 发布版（解耦版）：
  - 负责稳定 API、可安装分发、可文档化与可回归。
  - 只接收经过验证且具备回归证据的变更。

## 3. 同步原则
1. 先内后外：内部版验证通过后，才进入发布版同步。
2. 三件套同步：代码 + 测试 + 文档缺一不可。
3. 兼容优先：发布版行为变更必须评估接口兼容。
4. 证据驱动：同步必须附带“问题->根因->修复->验证”链路。

## 4. 同步门槛（发布前检查）
- 门槛A：内部版已有稳定复现与修复证明。
- 门槛B：发布版有对应测试（新增或回归）。
- 门槛C：用户文档与索引文档已同步。
- 门槛D：没有引入内部业务耦合依赖。

## 5. 改动分类与流向
- P0（生产风险）
  - 允许“内部版快速修 -> 发布版快速同步”，但必须先补最小回归。
- P1（逻辑增强）
  - 内部版完成一轮真实场景验证后再同步。
- P2（重构/风格）
  - 优先压后，不阻塞主线。

## 6. 版本策略
- 发布版版本号用于外部可追踪发布（如 v0.3.2/v0.3.3）。
- 内部版版本号用于阶段标识，不用于替代发布语义。
- 所有跨仓里程碑在 `work_history.md` 记录版本号与影响范围。

## 7. 已确认的历史教训（必须记住）
- 根因不清时跨仓同步，容易形成“双边都不完全正确”的状态。
- 仅同步代码不补文档与测试，会导致下个线程无法接力。
- 指针、fallback、评分这三类改动，必须有专项验证，不能靠肉眼。
